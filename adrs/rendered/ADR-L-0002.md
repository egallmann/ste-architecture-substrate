# ADR-L-0002: Artifact Authority and Schema Ownership

**Status:** proposed  
**Created:** 2026-05-02  
**Authors:** Erik Gallmann  
**Domains:** architecture, governance, schema-management  





---

## Context

The STE ecosystem has established patterns for schema authority across repositories.
ste-spec owns normative cross-repo Architecture IR contracts, adr-architecture-kit
owns ADR authoring schemas, and ste-runtime owns workspace extraction schemas.

ste-architecture-substrate introduces new artifact types (seeds, building blocks,
primitives, mutation rules) and must define clear schema ownership boundaries
that align with existing STE patterns.

This ADR defines what ste-architecture-substrate owns, what external systems own,
and how schema evolution and cross-repo coordination occurs.

### CAP-0004: Schema Definition

### CAP-0005: Schema Validation

Validate substrate artifacts against defined schemas using external validators

### CAP-0006: Schema Evolution

Version and migrate schemas with documented breaking changes


## Architectural Boundaries

### BOUND-0001: ste-architecture-substrate Ownership

**Description:**
Artifact structure schemas (seed, bundle, primitive, mutation rules), discovery
schemas (substrate-index, substrate-manifest)


**Rationale:**
Substrate owns its internal artifact model to enable independent evolution while
maintaining stable external interfaces


### BOUND-0002: ste-spec Ownership

**Description:**
Normative Architecture IR contracts (if substrate artifacts appear in IR)


**Rationale:**
Follows STE pattern where ste-spec owns all cross-repo interchange contracts


### BOUND-0003: adr-architecture-kit Ownership

**Description:**
ADR authoring schemas (ADR-L, ADR-PS, ADR-PC)


**Rationale:**
Follows STE pattern where adr-kit owns ADR authoring contracts; substrate uses
but does not redefine


### BOUND-0004: IaC Technology Ownership

**Description:**
Individual IaC technologies own structural validity rules (CloudFormation schema,
Terraform syntax, CDK type system)


**Rationale:**
Technology providers (AWS, HashiCorp, etc.) are authorities for their own IaC
syntax and semantics



## Interaction Contracts

### CONTRACT-0001

**Parties:** ste-architecture-substrate, consuming systems  
**Protocol:** JSON Schema files with $id and $schema references

**Guarantees:**
Schemas are valid JSON Schema (Draft 2020-12 or later). Schema $id fields
are stable URIs. Artifacts reference schemas via $schema field.


### CONTRACT-0002

**Parties:** ste-architecture-substrate, ste-spec  
**Protocol:** Byte-compare tests with sibling checkout, advisory CI checks

**Guarantees:**
Mirrored schemas are byte-identical to source. Contract guards detect drift
within one commit. MIRROR.md documents sync provenance.


### CONTRACT-0003

**Parties:** ste-architecture-substrate, consuming systems  
**Protocol:** Semantic versioning with documented migration paths

**Guarantees:**
Breaking changes increment major version. Migration guides provided for breaking
changes. Deprecated fields marked with deprecation notices.

## Decisions

### DEC-0008: ste-architecture-substrate owns artifact structure schemas (seed, building block,
primitive, mutation rules) and discovery surface schemas (substrate-index, substrate-manifest).


**Rationale:**
These schemas define the internal structure of substrate artifacts and how they
are discovered. Substrate is the authority for its own artifact model. Ownership
enables substrate to evolve artifact schemas independently while maintaining
stable external interfaces.





### DEC-0009: ste-spec owns normative cross-repo Architecture IR contracts if substrate artifacts
appear in Architecture IR.


**Rationale:**
Follows STE pattern: ste-spec is the single normative source for cross-repo
interchange contracts. If substrate artifacts are represented in Architecture
IR (e.g., for kernel admission or governance), the IR schema lives in ste-spec,
not substrate. Substrate may mirror schemas for validation (with contract guards).





### DEC-0010: adr-architecture-kit owns ADR authoring schemas (ADR-L, ADR-PS, ADR-PC).

**Rationale:**
Follows STE pattern: adr-kit defines stable authoring contracts for ADR YAML.
Substrate artifacts contain ADR bundles but do not redefine ADR schemas. This
maintains clear separation between artifact storage (substrate) and ADR authoring
(adr-kit).





### DEC-0011: Schema evolution follows semantic versioning with explicit migration paths for
breaking changes.


**Rationale:**
Substrate artifacts are long-lived and may be consumed by multiple systems across
versions. Semantic versioning (schema_version field) enables consuming systems
to detect compatibility. Breaking changes require migration documentation and
tooling support.





### DEC-0012: Contract guard and fixture sync patterns follow STE workspace conventions: test
fixtures for sibling schema synchronization, optional CI parity checks, mirror
provenance documentation.


**Rationale:**
When substrate mirrors external schemas (e.g., Architecture IR from ste-spec),
contract guards detect drift. Follows adr-architecture-kit pattern: byte-compare
tests when sibling checkout exists, advisory CI checks, MIRROR.md provenance.
Prevents silent schema divergence between repos.
