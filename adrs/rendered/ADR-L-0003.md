# ADR-L-0003: Mutation Rules Model

**Status:** proposed  
**Created:** 2026-05-02  
**Authors:** Erik Gallmann  
**Domains:** architecture, governance, infrastructure-as-code  





---

## Context

Architecture artifacts (seeds, building blocks) encode not just structure (IaC templates)
but also intent about how those structures should evolve over time. Some resources
should never change (immutable), others can be modified within bounds (mutable),
and others have conditional mutability based on context (conditional).

Mutation rules provide explicit, machine-readable constraints on artifact evolution
that guide AI decision-making and optionally feed external enforcement systems.
They embody the Ulysses contract model: normative guidance that maximizes compliance
by default while allowing explicit override.

This ADR defines the mutation rules model, constraint taxonomy, encoding approach,
and relationship to operational enforcement controls.

## Decisions

### DEC-0013: Mutation rules are explicit, machine-readable constraints on artifact evolution
encoded as sidecar YAML manifests.


**Rationale:**
Explicit constraints reduce ambiguity and enable deterministic AI guidance.
Machine-readable format (YAML) is consumable by both AI systems and humans.
Sidecar manifests (separate from IaC) avoid coupling constraints to IaC syntax
and enable technology-agnostic logical rules with technology-specific addressing.





### DEC-0014: Mutation rule constraint taxonomy: immutable (must not change), mutable
(can change within bounds), conditional (mutability depends on context).


**Rationale:**
Three-tier taxonomy balances expressiveness with simplicity. Immutable captures
"never change this" (e.g., S3 bucket name in production). Mutable captures "change
allowed with bounds" (e.g., instance type from t3.micro to t3.small). Conditional
captures "mutability depends on environment/stage/feature-flag" (e.g., encryption
required in prod, optional in dev).





### DEC-0015: AI guidance model: mutation rules maximize compliance by default, do not enforce
locally, enforcement is external to substrate.


**Rationale:**
Substrate guides AI toward compliant architectures by providing explicit constraints.
AI should respect mutation rules by default but can override with explicit intent
(Ulysses contract). Enforcement (CI checks, CloudFormation hooks, SCPs) is the
responsibility of external systems, not substrate. This preserves the boundary
between guidance (substrate) and enforcement (operational controls).





### DEC-0016: Mutation rules are technology-specific due to addressing model differences (CloudFormation
logical IDs, Terraform resource addresses, CDK construct paths).


**Rationale:**
Different IaC technologies use different addressing models. CloudFormation uses
logical IDs and property paths (Resources.MyBucket.Properties.BucketName). Terraform
uses resource addresses (aws_s3_bucket.my_bucket.bucket). CDK uses construct
paths. Technology-specific mutation rules enable precise targeting while maintaining
technology-agnostic logical intent.





### DEC-0017: Mutation rules relate to operational controls (stack policies, SCPs, hooks)
but do not replace them.


**Rationale:**
Mutation rules are authoring-time guidance. Operational controls (CloudFormation
stack policies, AWS SCPs, CloudFormation hooks) are runtime enforcement. Both
serve complementary roles. Mutation rules guide design decisions early (shift-left),
operational controls enforce at deployment/runtime. Optional: mutation rules
can be compiled to operational controls (e.g., Guard rules, stack policies) by
external tooling.





### DEC-0018: Alternatives considered: template metadata blocks (easy drift), Guard/OPA only
(not YAML, harder AI consumption), JSON Schema constraints (insufficient semantics),
stack policy as source (operational, not authoring guidance). Sidecar YAML selected
for machine-readability, AI-friendliness, and technology-specific addressing.


**Rationale:**
Template metadata blocks: risk drifting from actual properties as templates evolve.
Guard/OPA rule packs: powerful but DSLs are harder for AI to consume than YAML.
JSON Schema: good for type/bounds but doesn't encode immutable vs mutable vs
conditional semantics. Stack policy as source of truth: operational enforcement,
not authoring guidance; different intent. Sidecar YAML manifest selected for
balance of machine-readability, AI-friendliness, explicit addressing, and clean
separation from IaC syntax.
