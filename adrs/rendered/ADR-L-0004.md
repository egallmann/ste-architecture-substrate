# ADR-L-0004: Substrate Consumption and Discovery

**Status:** proposed  
**Created:** 2026-05-02  
**Authors:** Erik Gallmann  
**Domains:** architecture, integration, discovery  





---

## Context

Substrate artifacts (seeds, building blocks, primitives) must be discoverable
and consumable by external systems: adr-architecture-kit extensions (project into
ADR-PC), conversation engines (select and retrieve artifacts), and ste-runtime
(reference in workspace compilation).

The STE ecosystem has established file-based consumption patterns (conventional
paths, discovery bundles, manifests, sibling repo resolution) used by ste-kernel,
adr-kit, and ste-runtime. Substrate must follow these patterns for consistency.

This ADR defines the consumption interface, discovery mechanism, artifact resolution,
and integration model with existing STE systems.

## Decisions

### DEC-0019: Substrate uses file-based consumption interface following STE conventions: conventional
directory paths, discovery bundles, manifest files, sibling repo resolution.


**Rationale:**
Consistency with STE ecosystem. ste-kernel, adr-kit, and ste-runtime use file-based
consumption (no HTTP APIs, no service dependencies). Conventional paths enable
predictable artifact location. Discovery bundles (substrate-index.yaml) provide
machine-readable catalogs. Sibling repo resolution enables workspace-style multi-repo
integration. File-based approach is simple, portable, and works in offline/air-gapped
environments.





### DEC-0020: Discovery mechanism: substrate-index.yaml (entrypoint), substrate-manifest.yaml
(metadata), registries (artifacts by type).


**Rationale:**
Follows STE pattern used in adr-kit and ste-runtime: index file as entrypoint,
manifest for generation metadata, registries for typed artifact lists. Index
provides stable paths to registries and generation info. Manifest provides per-artifact
summaries and statistics. Registries enable technology filtering (list all CloudFormation
seeds, all Terraform bundles, etc.).





### DEC-0021: Artifact resolution: consumers read from conventional paths (seeds/, building-blocks/,
primitives/) via substrate-index references, with optional sibling repo resolution
for cross-repo integration.


**Rationale:**
Conventional paths reduce coordination overhead. Consumers know to look in seeds/
for seeds, building-blocks/ for bundles. Substrate-index provides canonical registry
paths (handles layout variations). Sibling repo resolution (../ste-architecture-substrate)
enables workspace-style consumption without hardcoded absolute paths.





### DEC-0022: Integration model: substrate provides artifacts, consuming systems perform projection,
interpretation, validation, and enforcement.


**Rationale:**
Clear separation of concerns. Substrate is a storage and structuring layer. adr-kit
extensions project seeds into ADR-PC (deterministic structure + interpretive
intent). Conversation engines select seeds based on conversation context. ste-runtime
may reference substrate artifacts in workspace manifests. Substrate does not
perform projection (no logic to convert seeds to ADRs), does not validate (consumers
own validation), does not enforce (external systems own enforcement).





### DEC-0023: Substrate does not provide HTTP API, service endpoints, or runtime query interfaces.

**Rationale:**
File-based consumption is sufficient for STE ecosystem use cases and avoids
operational complexity (no service to deploy, monitor, scale). Consuming systems
are local tools (adr CLI, ste CLI, conversation engine plugins) that access
file systems directly. If remote access needed in future, consuming systems can
implement (e.g., clone substrate repo, mount as volume, S3-backed file system).
