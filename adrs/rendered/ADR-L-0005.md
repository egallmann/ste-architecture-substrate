# ADR-L-0005: Corpus Maintenance and Discovery Sync

**Status:** proposed  
**Created:** 2026-05-02  
**Authors:** Erik Gallmann  
**Domains:** architecture, tooling, governance  





---

## Context

ADR-L-0004 (INV-0012) establishes that the discovery surface is derived and must
not be hand-authored. This creates an obligation: if the discovery surface cannot
be hand-edited, there must be a primary, repo-local capability to regenerate
and validate it from the authoritative corpus.

Without maintenance tooling, the corpus is difficult to extend. Adding a new
building block requires knowing exactly which discovery files to update and in what
format — a coordination burden that grows with the corpus size. For a fork-friendly
repo expected to be extended by downstream organizations, this friction is a
systemic barrier.

The workspace AGENTS.md contract guard rule requires that any repo committing
generated artifacts also provides a repo-local contract guard command. The
discovery surface (substrate-index.json, substrate-manifest.yaml, registries)
is a generated artifact. The contract guard obligation is therefore mandatory.

This ADR defines the corpus maintenance capability: what the tooling must do,
the invariants it enforces, and the behavioral contracts it provides to
contributors and automated systems.


## Capabilities

### CAP-0013: Corpus Sync

Regenerate the complete discovery surface (substrate-index.json,
substrate-manifest.yaml, discovery/registries/*.json) by walking
corpus/ and reading all metadata.json files.


### CAP-0014: Corpus Validate

Validate all corpus metadata.json files against their respective JSON Schemas
(seed.schema.json, building-block-bundle.schema.json, primitive-block.schema.json)
and report violations with file path and field context.


### CAP-0015: Corpus Contract Guard

Verify bidirectional integrity between corpus/ filesystem and discovery/substrate-index.json.
Exit non-zero on drift. Used as pre-push hook and CI gate.



## Architectural Boundaries

### BOUND-0001: Included Responsibilities

**Description:**
Corpus traversal, metadata file reading, schema validation, discovery surface
generation, bidirectional integrity checking, contract guard execution.


**Rationale:**
These are the minimal responsibilities required to fulfill the maintenance
capability and the AGENTS.md contract guard obligation.


### BOUND-0002: Excluded Responsibilities

**Description:**
Corpus artifact authoring, artifact deployment, schema evolution, ADR generation,
git operations (commit, push, tag).


**Rationale:**
Corpus authoring is a human/agent responsibility. Deployment is downstream.
Schema evolution is governed by ADR-L-0002. ADR generation is owned by
adr-architecture-kit. Git operations are out of scope for corpus tooling.



## Interaction Contracts

### CONTRACT-0001

**Parties:** contributor (human or agent), corpus_cli  
**Protocol:** Run corpus sync after any corpus/ mutation. Tool reads all metadata.json files,
validates structure, writes discovery files, exits 0 on success.


**Guarantees:**
Complete discovery surface written. All paths in output are relative to repo root.
Output is deterministic: same corpus state always produces the same discovery files.


### CONTRACT-0002

**Parties:** pre-push hook, CI pipeline, corpus_cli  
**Protocol:** Run corpus check before push or in CI. Tool verifies index ↔ filesystem
bijection, exits 0 if consistent, exits 1 if drift detected.


**Guarantees:**
Non-zero exit on any drift (orphan entries, missing files, unregistered artifacts).
Exit 0 only when index and corpus are fully consistent.



## Constraints

### CONST-0001 (technical)

**Description:**
Corpus tooling must not require network access

**Rationale:**
Supports offline development and fork usage

### CONST-0002 (technical)

**Description:**
Corpus tooling must not write to corpus/

**Rationale:**
ADR-L-0002 authority model — corpus artifacts are authoritative

### CONST-0003 (technical)

**Description:**
Corpus sync output must be deterministic

**Rationale:**
Deterministic output enables reliable git diff review of discovery changes


## Invariants

### INV-0014

**Statement:** The discovery index MUST contain exactly the set of artifacts present in
corpus/ (bijection: no orphan index entries, no unregistered corpus artifacts).
  
**Scope:** global  
**Enforcement:** must (test)  
**Verification:** automated

**Rationale:**
Prevents stale index entries and ensures all corpus artifacts are discoverable



### INV-0015

**Statement:** Corpus tooling MUST NOT modify corpus artifact files (metadata.json, templates,
mutation-rules.yaml). Corpus tooling writes only to discovery/.
  
**Scope:** global  
**Enforcement:** must (design)  
**Verification:** manual

**Rationale:**
Maintains artifact authority model defined in ADR-L-0002



### INV-0016

**Statement:** Corpus sync output MUST be deterministic: identical corpus state MUST always
produce identical discovery surface files.
  
**Scope:** global  
**Enforcement:** must (test)  
**Verification:** automated

**Rationale:**
Deterministic sync enables reliable code review and CI diffing





## Decisions

### DEC-0024: The discovery surface MUST be generated from corpus metadata files.
Discovery files MUST NOT be hand-authored as primary artifacts.


**Rationale:**
Hand-authored discovery creates drift risk: a contributor adds a building block
but forgets to update three discovery files. Generated discovery eliminates the
the category of "corpus added, index stale" errors by making sync explicit and
automatable. The metadata.json files in each corpus artifact are the single
source of truth; the discovery surface is a projection of those files.





### DEC-0025: A corpus sync command MUST regenerate the complete discovery surface
(index, manifest, all registries) from a single invocation.


**Rationale:**
Partial regeneration (e.g., sync only the seeds registry) leaves the system
in an inconsistent intermediate state. A single sync guarantees full consistency
in one operation. The cost of regenerating the full surface is negligible
(filesystem traversal over a small corpus).





### DEC-0026: A corpus check command MUST verify bidirectional integrity between the
discovery index and the corpus filesystem, and MUST exit non-zero on drift.


**Rationale:**
Bidirectional: (1) every entry in the index must resolve to a real file on disk;
(2) every artifact on disk must appear in the index. One-directional checks
(index-to-disk only) miss the case where an artifact is added to corpus but
not yet synced. Non-zero exit enables integration with pre-push hooks and CI.





### DEC-0027: Corpus check MUST be wired as a repo contract guard: either a pre-push hook
or a CI gate that runs on every commit touching corpus/ or discovery/.


**Rationale:**
Matches the workspace AGENTS.md contract guard rule (generated artifacts require
a contract guard command). A pre-push hook provides local enforcement before
push; CI provides enforcement for pull requests and direct pushes. Both are
preferred; at minimum the hook must exist.





### DEC-0028: Corpus tooling MUST be executable without package installation: a standalone
Python script runnable with the repo's standard Python environment.


**Rationale:**
A fork-friendly repo cannot assume pip-installable tooling is pre-installed.
A standalone script in tools/ lowers the barrier for forked organizations and
aligns with the "no ceremony" ethos of the project. If the tool matures, it
can be promoted to a proper CLI; the standalone-first approach does not
preclude that.





### DEC-0029: Corpus tooling MUST NOT write to corpus/; it MUST only read corpus/ and
write discovery/.


**Rationale:**
The corpus artifacts (metadata.json, templates, mutation-rules.yaml) are the
authoritative source of truth. Tooling that modifies them would violate the
authority model defined in ADR-L-0002. Discovery is the only writable surface
for corpus tooling.
